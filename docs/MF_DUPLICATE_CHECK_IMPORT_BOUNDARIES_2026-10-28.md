## 事業仮説への影響

**確認済み**：MFには既存仕訳の重複チェックがある。一方で、少なくとも上記2つの取込経路では、再インポートの重複リスクを利用者が管理する必要がある。これだけでは**有料の追加ツールが必要という証拠にはならない**。

**未検証の仮説**：STORES予約の事前決済を使うMF利用者が、MFの銀行連携・自動仕訳・仕訳重複チェックを使っても、予約/回数券/ 月謝の**確定入金内訳と振込額の差額説明**に月次で相当な時間を使うなら、追加価値があり得る。重複検出そのものではなく、振込の内訳を説明できるかを検証する。

## Issue #2：実CSV検証のゲート

- MFの**2つの取込経路**を混ぜない。公式テンプレートの実ファイルと必要な列・型・借貸/税区分を、対応する経路ごとに検証する。
- STORES予約の**予約一覧CSV**と**確定入金内訳（予約／回数券・月謝）**も別物。予約ID・決済ID・振込IDの対応は未確認。
- MFの「仕訳帳」重複チェックは**既存登録仕訳に対する操作**。CSV取込前の重複防止・銀行入金照合の実現を保証しない。
- 公式または個別許諾済み匿名化サンプルがない限り、実CSV適合は未検証のまま。顧客の生CSVを公開GitHubに保存しない。

## 2026-10-28追加検証：MFの「取引No」はSTORES決済ID・再取込防止キーではない

**公式仕様の重要な発見（既存出典O021を再精査、URLの重複登録なし）**：MFの「仕訳帳」CSVにおける「取引No」は、外部決済を一意に追跡するためのキーではなく、**単一／複合仕訳の判別に使う番号**。同じ会計年度で既に使用済みの番号を指定しても、MFは「最大取引No+1」に置き換えて**新しい仕訳として取り込む**。したがって、STORES側の決済IDをこの列に埋めても、再インポート防止や予約・入金への逆引きが保証されるわけではない。

- 取引Noは**9桁以内の数字**。外部サービスのIDが文字列や10桁以上なら、そのままの転記は仕様に合わない。
- 複合仕訳として扱う条件は**同じ取引No、同じ取引日、借貸合計一致**の3つ。番号が同じでも日付や借貸が異なれば同一複合仕訳と決めつけない。
- 取引日の指定形式は **yyyy/MM/dd**。インポート可能なのは現在選択している会計年度の取引日のみ。
- 勘定科目の名前がMF登録名と一致せず、画面で追加・変換せず進むと**未確定勘定**になる。税区分の不一致も、変換しない場合は**科目のデフォルト税区分**が使われる。**CSVファイルを受け付けたことと、会計上の正しい仕訳が登録されたことは別**。
- これらはMFが公開する**公式仕様**であり、利用者の作業時間・追加課金需要の証拠ではない。

公式一次資料：[MFクラウド会計「仕訳帳」をインポートする](https://biz.moneyforward.com/support/account/guide/import-books/ib01.html)（**2026-07-09更新、2026-10-28確認**）。既存の台帳 `O021` と同一URLなので、新規の公式根拠件数にも加算しない。

### Issue #2：実CSV適合検証で追加すべき具体的な受入条件

| 検証 | 合成データで先に再現すべき例 | 合格条件（本番の互換性認定ではない） |
| --- | --- | --- |
| 外部IDとMF取引Noの分離 | STORES決済IDが英数字・10桁以上／同一Noを再利用 | IDの同一性を仮定せず、MFの9桁制限と重複時の採番を明示。別途参照キーの出典と保管方法を決める |
| 複合仕訳のまとまり | 同一No+日付+借貸一致／日付不一致／貸借不一致 | 3条件を個別に検査し、未確認ケースは「要確認」に留める |

| 再取込 | 同じ合成仕訳帳CSVを2回インポートする想定 | 取引Noの一致だけで重複回避できると主張しない。**実MFへのインポートはまだ行っていない** |
| STORESとの照合 | 予約一覧・確定内訳2種類・銀行記録で参照値が異なる想定 | 決済ID・返金ID・入金参照値の対応が確認できるまで振込単位の照合を「実装済み」としない |
