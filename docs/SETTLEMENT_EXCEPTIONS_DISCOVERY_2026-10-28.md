# 月謝再請求・振込保留が月次照合に与える影響と需要検証（2026-10-28）

対象: Issue #2（実CSV適合）、Issue #3（有料需要）。**公式仕様の発見であり、実利用者の困りごとや有料需要の証明ではない。** 実CSV取得・営業・決済・公開デプロイなし。

## 新たに確認した公式事実（各URLは独立した公式FAQ）

1. **月謝の請求失敗と自動再請求**：STORES予約の月謝は原則毎月1日に当月分を自動請求。1日に決済が完了しなければ、翌日から月末まで自動請求が行われる（公式、2025-10-17更新）。
   - https://reserve-faq.stores.jp/hc/ja/articles/28718010515481
2. **月謝の決済完了日による振込月の違い**：通常の月次サイクルでは、1日に請求完了なら当月25日、2日以降に請求完了なら翌月25日（休日は翌営業日）。公式例は6月1日決済→6月25日、6月2日決済→7月25日。週次入金は別ルールであり、この月次の例を転用しない（公式、2025-10-17更新）。
   - https://reserve-faq.stores.jp/hc/ja/articles/47636371793049
3. **振込口座の名義審査で入金が保留される**：審査中に入金日を迎えると振込は実行されず、審査完了後の次回入金日に未入金分が合算される。否決なら当該口座では振り込まれず、正しい口座の登録・審査後の次回入金日に合算（公式、2026-07-31更新）。
   - https://reserve-faq.stores.jp/hc/ja/articles/56991113242649

既存の公式仕様（再計上しない）：通常決済のUTC境界・週次入金は `docs/STORES_SETTLEMENT_PERIOD_2026-10-28.md`、1万円未満繰越と手数料は `docs/STORES_PAYOUT_FEES_AND_TAX_TRANSITION_2026-10-28.md`、入金内訳の2種類は `docs/PAYOUT_SOURCE_CONTRACT_2026-10-28.md` に記録済み。

## 何が「売上はあるが銀行入金がない」の原因候補か

| 合成ケース（実取引ではない） | 公式から確実に言えること | 確認できないこと |
| --- | --- | --- |
| 月謝6/1請求失敗、6/2決済完了、月次振込 | 公式の例では7/25振込対象。**6月分の月謝＝6月の銀行入金**ではない | 6/2の実決済時刻、実ファイルの決済状態、手数料、銀行着金 |
| 月謝6/1決済完了、月次振込 | 公式の例では6/25振込対象 | 返金、繰越、振込手数料、組戻し等を経た最終着金 |
| 口座名義審査中のまま振込日を経過 | 審査完了まで保留、次回入金日に合算 | 口座名義審査の実ステータスをCSVから取得できるか |
| 口座名義審査否決 | その口座には振込されず、登録・再審査完了後に未入金分を合算 | 再審査日、振込実行日、実際の明細の紐付け |

**重要な区別**：月謝の「請求日」「決済完了日」「サービス対象月」「振込予定日」「振込実行日」「銀行着金日」は別。1万円未満繰越・返金・口座名義審査・組戻しを同一原因として自動分類しない。公式の月謝FAQは日付単位の説明であり、UTC境界と組み合わせた個別取引の確定ロジックを証明するものではない。

## Issue #2：実CSVの受入条件（まだ一件も検証していない）

- 「入金履歴：内訳（予約）」「入金履歴：内訳（回数券・月謝）」の**両方**を対象とし、月謝再請求がどちらのファイルのどの行・列に表れるか確認。
- 請求日と実際の決済完了日時、請求失敗・再請求の状態、対象月、振込参照値、確定額の列有無を**実ヘッダーで確認**。無い情報を推測で埋めない。
- 振込予定と実行済みの区別、審査中/否決/組戻しの判別情報がCSVに存在するか、入金画面の別情報が必要かを確認。
- 実際の銀行入金は、権利者の個別承認がある場合のみ、**非公開・匿名化された検証手順**で突き合わせる。第三者の生CSVや口座番号・顧客名をGitHubに置かない。
- CSVの公式公開サンプル・許諾済み匿名化サンプルは未入手。**実CSV適合=false、現行アプリの自動銀行照合は未実装**。

## Issue #3：本人の実作業を確かめるための反証優先ヒアリング（連絡は未承認）

**適格条件**：STORES予約の事前カード決済または月謝・回数券の入金があり、MFクラウド会計を実際に使用し、直近の月次締めを本人が実施した事業者。STORESレジ/ネットショップの連携だけの利用者は混ぜない。

1. 直近の月次締めを**実際に何分**かけたか、MF標準のSTORES連携・銀行明細・Excelでどこまで解決したかを、製品案を見せる前に尋ねる。
2. 直近3か月に「月謝1日決済失敗→2日以降成功」「口座審査保留」「1万円未満繰越」「期限後返金」がそれぞれ**何件実際にあったか**を確認。ゼロ件なら「未経験」と記録し、困りごとを捏造しない。
3. 発生した事象のうち、**既存のSTORES入金履歴とMF機能では説明できず**、人が何分費やしたかを特定する。単なる入金日ずれを高価な有料機能とみなさない。
4. 既存代替策を見せた後で、現状MVP（CSV検査・仕訳候補のみ）と**未実装の入金自動照合**を別々に説明し、各案の月額2,980円を支払う条件・決裁者・購入時期を具体的に尋ねる。肯定的な感想を「具体的な支払い意思」と数えない。

**検証の反証条件**：適格者が実際にはMF標準機能で十分、該当例外がほぼゼロ、削減時間が料金に見合わない、または価格を提示しても具体的な購入条件が出ない場合、MF限定・月額2,980円仮説を縮小/変更する。第三者への送信・実顧客データ取得は個別承認まで停止。

## 証拠の取り扱いと現在地

公式FAQ3件は `official_capability` として別URLで記録する。**一次利用者の体験談、MF利用者、同意済みヒアリング、支払い意思には加算しない**。本日の公開検索ではSTORES予約+MFを併用する本人の具体的な月次照合体験談は新規確認できなかった。
