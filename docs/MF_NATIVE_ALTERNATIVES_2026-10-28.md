# マネーフォワード標準機能との競合検証（2026-10-28）

対象: Issue #3（有料需要）と Issue #2（実CSV適合）。**今回の重要な新発見は、MFクラウド会計自体が銀行明細の自動取得・CSV取込・自動仕訳ルールを持つこと。** 「銀行CSVを読み込む」「入金明細を自動仕訳する」だけでは、月額の独自価値として不十分。既存製品の機能を作り直す前に、**STORES予約の内訳との照合**が実際に必要か検証する。

## 1. 公式情報から確認できた既存の代替手段

| 業務 | マネーフォワード公式で確認できたこと | 本製品への判断 |
| --- | --- | --- |
| 銀行・カード取引の取得 | 「データ連携」で取得した取引明細から「連携サービスから入力」に仕訳候補を作成できる | 銀行明細の取得自体を差別化機能として売らない |
| 銀行取引CSVの取り込み | 銀行等のサイトからダウンロードしたCSVまたはANSER形式の取込が可能。所定サンプルの必須情報は日付と金額 | 「銀行CSVインポート」を独自の有料価値とみなさない |
| 明細の仕訳候補とルール | 自動仕訳ルールにより、取得した明細の摘要等に応じた勘定科目を設定できる。明細からの候補を確認して登録する | 「銀行入金を仕訳候補にする」だけでは重複 |
| STORES予約の売上データをMFへ直接自動連携 | STORES予約の公式FAQは、STORES予約単体からMF/freeeへの売上・決済データの自動連携を**非対応**と明記 | **STORES側の決済内訳とMF側の銀行入金の橋渡し**には未解決の余地があるが、顧客需要は未検証 |
| STORES予約の確定入金内訳 | STORES予約の公式FAQは、予約と回数券・月謝の2種類を入金履歴から別ダウンロードするよう説明 | 銀行の振込1件をSTORES内訳に説明可能な形で結びつけられるか、実CSVのキーと粒度が未検証 |

**重要な限定**: 「MFが銀行取引を取得できる」ことは「STORES予約の予約ID・決済ID・返金・手数料と1件単位で照合できる」ことを意味しない。逆に、MFの標準機能だけで十分な顧客には本製品を売る理由がない。銀行CSVをMFが読めるとしても、任意のSTORES入金内訳CSVがMFの銀行明細CSVとして読み込めるとは確認していない。

## 2. 差別化の対象を狭くする（仮説、未実装）

**現行のMVP**: 予約等のCSVを手動マッピングして要確認を抽出する試作品。銀行入金との自動照合・返金仕訳は**未実装**。実STORES CSV・MF会計インポートも未検証。

**これから検証する価値仮説**: MFが銀行明細を取得した後に、STORES予約の確定入金内訳（予約 + 回数券・月謝）と突き合わせ、**なぜ銀行入金額が予約売上合計と異なるのか**を説明し、差分だけを要確認にする。手数料、UTC基準の入金対象期間、返金、少額繰越の扱いを分離する。

この価値仮説が成立するには、**MF標準機能を既に使っている事業者でもなお、実際の手作業が残っている**必要がある。対象となる事業者の人数・実際の困りごと・毎月の所要時間は確認できていない。

| 検証すべき工程 | MF標準機能で解決済みか | 本ツールが増分価値を出せる条件 |
| --- | --- | --- |
| 銀行振込の記録を取り込む | 自動連携またはCSV取込がある | 原則として対象外 |
| 銀行明細の仕訳候補を作る | 自動仕訳ルールがある | 原則として対象外 |
| STORES予約の確定入金内訳を取り込む | **直接連携の有無は未確認** | 公式/許諾済み匿名化サンプルで形式と取引粒度が確認できる |
| STORESの予約・回数券・月謝・返金・手数料を振込単位で説明 | **MFの上記公式ガイドだけでは確認できない** | 顧客が実際に手作業で照合し、削減可能な時間が測れる |
| 同じ売上を会計に二重登録しない | MFの既存運用方法に依存。現行MVPでも保証なし | 顧客の現在の登録フローを確認してから検証する |

「確認できない」は「機能が存在しない」と同義ではない。MFクラウド会計とMFクラウド債権管理・請求書Plusなど**別製品の機能は混同しない**。

## 4. 判断・停止条件

- **MF標準機能で十分**な利用者が多い、または残る照合時間が短いなら、CSV加工の月額サブスクを優先しない。単発売り切り、別業務への転換、または停止を検討する。
- STORES入金内訳に安定した照合キーがなく正確な突合ができない場合、「自動入金照合」を販売しない。検査レポートに留めるか対象を見直す。
- 一次体験談5件・同意済みヒアリング5件・具体的支払意思3件・実CSV適合が揃うまでは有料化Goを保留。
- **今回の調査では新しい実利用者の一次体験談を確認できていない**。公式ガイドを「顧客の声」に数えない。
- 第三者への営業送信、顧客の実CSV取得、有料契約、決済、公開デプロイはユーザーの個別承認なしに実施しない。氏名・連絡先・取引明細を公開GitHubに記録しない。

## 5. 次の具体的な検証順

1. STORES予約 + MF会計を併用している**本人の公開体験談**を探す（現時点はfreeeの事例1件のみ）。
2. MFの口座連携・自動仕訳ルールを使ってもなお残る**STORES固有の月次照合**を本人の具体的な作業から特定する。
3. 公式サンプルまたは許諾済み匿名化サンプルで、入金履歴の予約・回数券/ 月謝の2種類と銀行振込の識別子を検証する。
4. 需要・実CSV適合の両方を満たした場合に限り、増分の作業時間短縮を実測して価格を再検討する。

## 2026-10-29：MF利用者の別POS導入事例を「月額課金の反証対照」として採否判定（Issue #3）

**新規確認した固有の根拠**：[MF公式掲載の美容室導入事例（公開2017-07-06）](https://biz.moneyforward.com/case/110/)。店舗担当者の本人発言では、MFクラウド確定申告と**Squareレジ**を組み合わせ、以前は月末に取引データをアップロード／手入力していたが、導入後は毎日データが自動取得され、月末の入力作業が不要になったと説明する。銀行・カードの明細取得とSquareの売上連携を区別している。**出典はMF販売者が掲載する販促事例**であり、独立レビューではない。2017年の本人申告で、現在の連携保証・実測削減時間・購入意思を示さない。

**対象判定：不採用（STORES予約利用の記述なし）。** MF利用の実作業に関する本人発言ではあるが、STORES予約の2入金内訳との月次照合経験、月額2,980円への支払意思、現行CSV適合の証拠ではない。既存の本人一次体験談7件・M2掲載時期確認済み5件・対象MF月次照合0件には**加算しない**。新しい需要証拠は0件。公開出典を1件確認したことと、顧客を1件獲得したことは別。

**価格仮説への反証条件を明確化**：対象事業者の既存MF連携または別の統合POSで、月末のSTORES固有の照合が既に不要なら、本ツールの月額2,980円の増分価値は支持されない。実際の顧客では「MF標準連携／Square等の代替導入後も、STORES予約の確定入金内訳2種類と銀行振込の突合が毎月何分残るか」を先に確認する。ゼロなら肯定証拠に数えず、単発売り切り／対象変更／中止を比較する。Squareへの移行が現実的・安価だと推測するものではない。

**今回の完了範囲**：公開事例の掲載日・実作業・製品・媒体バイアス・不採用理由を既存比較資料とM5台帳に反映。実顧客CSV・面談・外部連絡・決済なし。M3は実ヘッダーと振込キー未確認のため in_progress のまま。次の1作業は11/03期限のM3について、公式公開の真正な現行入金内訳ファイルが新規に確認できた場合のみ実ヘッダー・共通振込キーを受入仕様に照らして検証すること。
